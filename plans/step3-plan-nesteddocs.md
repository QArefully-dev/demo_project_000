## Scenarios

### 1. A configured blend survives basket, checkout, and confirmation (AC1, AC3, AC6)
**Behaviour:** a signed-out customer builds a compatible blend, adds it to the basket, and the same blend — composition, classification, and price — is what checkout and the order confirmation show.
**Starting state:** fresh browser context (no cart cookie), on `/custom-blend`. Seeded base "Portland Cement" (`cementitious-materials`, non-food) with seeded ingredient "Tile Grout" (same mixing group) — both confirmed present in the running app's base/ingredient pickers.
**Steps:** choose Portland Cement as base -> select Tile Grout as the only ingredient (auto-fills to 50/50) -> confirm the summary shows classification "Non-food blend" / "Not for consumption" and a blend total -> click "Add blend to cart" -> from the basket, confirm exactly one line for Portland Cement carrying the custom-blend badge, the same blend total, and an "Edit blend" link -> continue to checkout -> complete delivery, schedule, and payment steps -> land on order confirmation.
**Observable outcome:** the basket line, the checkout summary line, and the order confirmation all show the same composition ("50% Portland Cement — 50% Tile Grout"), the same non-food classification and handling notice, and the same blend total. A mismatch in any one of the three is the failure.
**Data:** Portland Cement / Tile Grout are seeded, real accessible names confirmed by driving the running app; the observed blend total was $403.25 at 4 sacks (the seeded MOQ) — pin this and the composition string as named constants once confirmed against `e2e/README.md`-documented seed facts (not yet present there for Custom Blend; add them).
**Deliberately not covered:** the exact pricing/tier/pigment math behind the total — that's the API's job and is already unit- and integration-tested (see Existing coverage).

### 2. The server's pigment cap blocks submission and preserves the draft to be corrected (AC4)
**Behaviour:** a combination the configurator lets the customer assemble is rejected by the server, the rejection reads clearly, the blend is not added, and the customer can fix it in place rather than starting over.
**Starting state:** fresh `/custom-blend`, base "Plaster of Paris" (`casting-materials`), which — unlike most bases — accepts a `pigments`-group ingredient the client-side rules alone do not cap at 10%.
**Steps:** choose Plaster of Paris as base -> select ingredient "Dry Pigment - Iron Oxide Red" (auto-fills to 50%, confirmed above the 10% pigment cap) -> observe the live evaluation result.
**Observable outcome:** an alert reading "Pigment content cannot exceed 10% (selected: 50%)" appears, "Add blend to cart" is disabled, and the ingredient stays selected. Then reduce the percentage to 10% via the ratio control: the alert clears, the total appears, and the button becomes enabled — proving the draft was never discarded. Never click "Add blend to cart" mid-error; the point is that submission is blocked, not that a bad request round-trips.
**Deliberately not covered:** other rejection codes (`CUSTOM_BLEND_INCOMPATIBLE`, base-range, whole-percentage) — the pigment cap is the one boundary that is reachable purely through normal UI interaction (compatible-but-server-capped), and one coded rejection proves the wiring; the others are exhaustively unit-tested (see Existing coverage) and would not prove anything new in a browser.

### 3. Editing a basket line replaces it instead of duplicating it (AC5)
**Behaviour:** editing a configured blend already in the basket reopens the configurator with the existing choices loaded, and saving replaces that line.
**Starting state:** basket already containing one configured blend (build it via scenario 1's first steps, or reuse that basket if run after it — but written so it does not depend on run order: this scenario adds its own blend first).
**Steps:** from the basket, click "Edit blend" -> confirm the configurator opens in edit mode (heading "Edit your custom blend", base and quantity shown read-only, the original ingredient pre-checked) -> change the ingredient percentage -> click "Update blend".
**Observable outcome:** the basket still shows exactly one custom-blend line (not two), now reflecting the new percentage/total, and the line's batch mark differs from the pre-edit one (a fresh server-issued key). Assert the basket's line *count* for this product stays at one, not just that the edited values appear.
**Deliberately not covered:** concurrent edits from two tabs, or editing after the line's facts changed server-side — plausible but speculative without a way to force it through the UI.

## Existing coverage

Extensive, and it changes what belongs at E2E level:

- **apps/web/src/features/customBlend/CustomBlendReachability.integration.test.tsx** already drives the real router+DOM (jsdom, mocked API) through: nav reachability, a `baseVariantId` deep link, sold-out ingredient selectability, mixed-group totals/classification/submit-gating, stale-evaluation dropping after a ratio change, and an invalid `baseVariantId`. This is effectively AC1–AC4 at the integration level already.
- **apps/web/src/features/customBlend/CustomBlendPage.test.tsx** covers the submit gate closing until an exact server verdict exists, a rendered pigment-cap verdict with submit disabled, non-food classification from the server, and replacing an edit target with a newly resolved key (AC2–AC5), all against a mocked API.
- **apps/web/src/features/customBlend/useCustomBlendEvaluation.test.tsx** covers the 150ms debounce, abort-and-drop of stale requests, and coded-error retry — the mechanics behind AC2's "no page reload" and part of AC4.
- **apps/api/test/customBlend/customBlendRulesJourney.integration.test.ts** runs a full mixed-group blend through evaluation, cart, and a real V10 checkout convergence (AC6), and a **separate test in the same file** ("stale mixed-group Custom Blend fails before gateway and preserves business state") proves a blend that passed evaluation is rejected before payment and the order/cart state stays consistent — this is AC4 at the checkout boundary, already covered server-side.
- **apps/api/test/customBlend/customBlendEvaluation.integration.test.ts** and **customBlendOptions.integration.test.ts** cover the pigment cap, compatibility, country exclusions, and base/option listing edge cases exhaustively at the API layer.
- No existing `e2e/*.spec.ts` touches Custom Blend, the basket, or checkout at all — `e2e/catalog.spec.ts` is the only spec, and it is search-only. There is no e2e page object for the configurator, basket, or checkout to extend.

Given this, the three scenarios above deliberately do **not** re-enumerate compatibility rules, pricing math, or every rejection code — that would just re-run the integration suite through a browser. They instead prove what only a real browser can: a real network round trip through the Vite proxy, state carried across real page navigations (basket -> checkout -> confirmation), and one concrete "screen allowed it, server didn't" case reached through ordinary UI interaction.

## Risks

- **No checkout page object exists.** Scenario 1 is the only one that needs one, and it is the most expensive to build (delivery address, slot, billing, payment steps). If only a subset of this plan gets implemented, scenarios 2 and 3 (configurator-only) are far cheaper and should come first.
- **Ticket vs. app: AC4's "the screen allowed me to build"** most naturally reads as a client-side race (evaluation succeeds, then a mutation-time fact changes before Add is clicked) rather than the pigment-cap case chosen here, which the live evaluation catches immediately. The mutation-time race (add succeeds at evaluation but the API rejects at the actual `POST` moments later) is not reachable through ordinary UI timing and has no existing coverage anywhere — worth flagging to the ticket author as a gap neither the ticket's wording nor any test currently resolves. Scenario 2 is the closest realistic substitute reachable through the UI.
- **Money and composition strings in scenario 1 are read from the currently seeded catalog**, not from a documented fixture — `e2e/README.md` has no Custom Blend section yet. `npm run reset` reseeding could change stock, price, or which SKUs pair, silently breaking a hardcoded total. Implementer should pin the base/ingredient names and re-derive the total once at write time, and add them to `e2e/README.md`.
- **Flakiness sources:** the 150ms evaluation debounce (scenario 1's total should be asserted with a web-first `toHaveText`/`toContainText`, never a fixed wait); the three-step checkout flow accumulating state client-side across steps (a failure partway through should not silently retain a stale step); and cart identity being stored client-side, so each scenario needs its own fresh browser context rather than sharing one across the file.
- **Scenario 3 assumes editing preserves the pre-edit ingredient selection on load** — confirmed by driving the app (edit mode shows "1 of 4 ingredient selected"), but the exact heading/URL shape should be re-checked at implementation time in case the country or locale under test changes copy.

## Approach

Build the configurator-only page object first (`custom-blend-page.ts`, mirroring `catalog-page.ts`'s locator-only style) and land scenario 2 (pigment cap) — it needs no basket or checkout support and directly proves AC4's most reachable form. Next, add a minimal `cart-page.ts` and land scenario 3 (edit replaces the line), which only needs basket + configurator, not checkout. Scenario 1 comes last: it needs a new `checkout-page.ts` covering all three checkout steps, which is the largest single addition, but by that point the configurator and basket locators already exist and only the checkout portion is new. Confirm the seeded base/ingredient names and the resulting total once against the running app immediately before writing each spec, since none of this is pinned in `e2e/README.md` yet.
