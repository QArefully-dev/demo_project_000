## Scenarios

### 1. Happy path: configure a blend and see it through to order confirmation (AC1, AC6)
**Behaviour:** a signed-out customer builds a valid blend, adds it to the basket, and it survives checkout to the confirmation screen with consistent pricing.
**Starting state:** signed-out session, default `US` country. Base material `Whey Protein Isolate` (SKU `SPN-0008-001`) and ingredient `BCAA material` (SKU `SPN-0012-001`) — both seeded, food-grade, `Sports Nutrition`. No pre-existing cart.
**Steps:** open `/custom-blend`, click "Use Whey Protein Isolate as base", check "BCAA material", leave the default 50/50 split, click "Add blend to cart", click "View cart", then "Continue to checkout" and complete payment with the standard test card (`4242 4242 4242 4242`) and a valid delivery/billing selection.
**Observable outcome:** the recap screen shows heading "Custom blend added to your cart" and composition text "50% Whey Protein Isolate — 50% BCAA material"; the basket shows exactly one line tagged "Custom blend" with a "Blend total" figure; checkout's summary shows the same blend total; the confirmation page (`/order-confirmation/:orderId`) shows a "Custom blend" line with the same material total, blending fee, and blend total figures seen in the configurator summary.
**Deliberately not covered:** exact money arithmetic (tier discounts, blending fee formula) — that's proven by [customBlendRulesJourney.integration.test.ts](apps/api/test/customBlend/customBlendRulesJourney.integration.test.ts) and [customBlendCheckout.integration.test.ts](apps/api/test/checkout/customBlendCheckout.integration.test.ts). This scenario only proves the figures shown to the user agree across the three screens.

### 2. The server rejects a combination the screen allowed, and the draft survives (AC4)
**Behaviour:** an unacceptable combination is caught server-side, reported clearly, kept out of the basket, and the user's in-progress configuration is not discarded.
**Starting state:** signed-out session. Needs a base/ingredient/percentage combination the picker lets you assemble but the evaluator rejects — the pigment cap rule exercised in [customBlendEvaluation.integration.test.ts](apps/api/test/customBlend/customBlendEvaluation.integration.test.ts) ("pigment cap exposes safe metadata") is the concrete candidate; confirm the exact base/ingredient pair and cap threshold against that test (or by probing `/api/custom-blends/options` and `/evaluate` in the browser) before writing the spec, since I did not reproduce the rejection in the browser myself.
**Steps:** assemble the flagged combination, wait for the (debounced) evaluation, attempt "Add blend to cart".
**Observable outcome:** a clear rejection message renders in the summary area (not a silent disabled button — AC3/AC2 already prove the disabled-button path), no navigation to the basket occurs, and the base/ingredient/percentage selections are still visible in the form afterward.
**Deliberately not covered:** enumerating every rule the evaluator can reject on — one clear rejection path is enough at this layer; rule-by-rule coverage belongs to the integration suite.

### 3. Editing a blend already in the basket replaces the line, not adds a second one (AC5)
**Behaviour:** editing a basket blend reopens the configurator pre-filled, and saving replaces that exact line.
**Starting state:** signed-out session with one configured blend already in the basket (built the same way as Scenario 1, or via a `beforeEach` that repeats those UI steps since there is no seeded cart to reuse).
**Steps:** on `/cart`, click "Edit blend" on the line (this navigates to `/custom-blend?baseVariantId=...&editConfigKey=...`), change the ratio slider to a new valid split, submit, then return to the basket.
**Observable outcome:** the configurator loads with the existing base and ingredient pre-selected before any edit; after saving, the basket still shows exactly one blend line (assert count, not just presence), with the composition text reflecting the new ratio.
**Deliberately not covered:** the `authoritativeConfigKey` reconciliation logic between a stale and fresh key — that's unit-tested in [CustomBlendPage.test.tsx](apps/web/src/features/customBlend/CustomBlendPage.test.tsx) ("preserves edit quantity while replacing with a newly resolved key").

### 4. Live price preview updates without a page reload (AC2)
**Behaviour:** changing a ratio updates the material total, blending fee, and blend total in place.
**Starting state:** signed-out session, base `Whey Protein Isolate` + ingredient `BCAA material` selected (as in Scenario 1).
**Steps:** read the three summary paragraphs ("Material total: …", "Blending fee: …", "Blend total: …") at the default 50/50 split, change the percentage via the "BCAA material percentage" spinbutton to a different valid value, wait for the debounced evaluation.
**Observable outcome:** all three figures change to new values and the URL/page does not reload (e.g., assert the base picker/step-1 selection is still present without a navigation event). Pin the two ratios' totals as named constants once confirmed against a captured run, rather than asserting only "changed".
**Deliberately not covered:** the debounce timing itself and stale-response discarding — covered by [CustomBlendPage.test.tsx](apps/web/src/features/customBlend/CustomBlendPage.test.tsx) ("drops a stale evaluation when the percentage changes before the fresh verdict").

### 5. Safety classification and non-food handling guidance are visible (AC3)
**Behaviour:** the summary states food-grade vs non-food, and non-food carries handling guidance.
**Starting state:** two configurations — one all-food-grade (Scenario 1's Whey Protein Isolate + BCAA), and one with at least one non-food component (e.g., a `Trade & Creative Materials` or `Household & Cleaning` base/ingredient pair — confirm an exact eligible pair via the options endpoint or picker before writing, since none was captured in this session).
**Observable outcome:** the food-grade configuration shows a region/label "Food-grade blend blend" (as seen: `region "Food-grade blend"`); the non-food configuration shows the non-food equivalent plus visible handling/PPE guidance text.
**Deliberately not covered:** the specific wording of every handling-guidance string — this scenario checks that guidance text is present, not its full copy, since copy is localisation-owned.

## Risks

- **Scenario 2's exact rejection trigger is unverified in the browser.** I saw the pigment-cap rule only in the API test file, not by reproducing a rejection through the UI. An implementer must confirm the concrete base/ingredient/percentage combination (and resulting message) with `playwright-cli` before coding the spec, or the scenario will not compile as written.
- **Non-food base/ingredient pair for Scenario 5 is unverified.** I only confirmed the food-grade label text (`region "Food-grade blend"`) in the browser; the non-food label text and a concrete eligible non-food pair need the same confirmation.
- **No seeded cart exists for these specs.** Every scenario that needs "a blend already in the basket" (3, and setup for 5) must build it via real UI steps first, which makes those tests slower and gives two failure points (build-up, then the actual assertion) — keep the build-up in a shared helper/page-object method, not copy-pasted per test, and keep it out of the timed assertion.
- **Checkout in Scenario 1 depends on delivery/billing/payment fixtures** not yet explored in the browser (destination, slot, card fields). These exist and are used by existing checkout specs' page objects if any exist — none currently do in `e2e/pages/`, so a `checkout-page.ts` object will need to be built from [CheckoutPage.tsx](apps/web/src/features/checkout/CheckoutPage.tsx), which adds scope beyond the Custom Blend feature itself.
- **Ordering/tier-discount figures are deployment-sensitive.** The "Material total"/"Blending fee"/"Blend total" figures I captured (e.g. `$1,318.25`) reflect current seeded prices; if `npm run reset` reseeds with different prices these break. Pin them as named constants with a comment, per repo convention, and expect them to need updating after a reseed — same risk the existing `catalog.spec.ts` calls out for its own constants.
- **Cross-scenario contamination via a shared anonymous cart.** The app appears to key the cart to the browser session/cookie rather than requiring login; scenarios 1, 3, and 5's basket setup must each start from a fresh browser context (per Playwright's default) so a leftover line from one test doesn't make another test's "exactly one line" assertion pass or fail for the wrong reason.

## Approach

Start with a single new `e2e/custom-blend.spec.ts` and a `e2e/pages/custom-blend-page.ts` page object (base/ingredient/ratio locators, "Add blend to cart"), extended by a minimal `cart-page.ts` (line count, "Edit blend" link, quantity/remove controls) since the basket is load-bearing for three of the five scenarios. Build Scenario 1 (happy path) first — it forces the checkout page object into existence and gives every other scenario a template for basket setup. Land Scenario 3 (edit) next since it reuses that setup almost unchanged. Confirm Scenario 2's exact rejection trigger and Scenario 5's non-food pair with `playwright-cli` before writing them, rather than guessing at seeded data. Scenario 4 (price preview) is cheapest and can be written any time once the base/ingredient picker locators exist.
